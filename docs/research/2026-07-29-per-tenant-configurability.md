# Per-tenant configurability without a configuration engine

Date: 2026-07-29

How successful vertical SaaS products give each onboarded business its own terminology, its own record categories and custom fields, and its own approval/handoff flows — without building the configuration engine `ARCHITECTURE.md` §13 decision 1 already refused.

Everything below is sourced to vendor documentation, first-party engineering writing, or the authors' own essays. Where a source could not be read, that is stated rather than papered over.

---

## Executive summary

The research produced one dominant finding, and it is not the one the question implies.

**No mature vertical SaaS product in this category ships a configuration engine, a workflow graph, or per-tenant terminology renaming.** Fleetio, Samsara, ServiceTitan, Jobber and Odoo were surveyed against their own API schemas and admin docs. Zero of five let a customer define an arbitrary workflow graph. Approval, where it exists, is a bounded rule — role plus threshold, or an ordered list of role-scoped steps. Terminology renaming exists in exactly two of the five, and in both cases it is a single two-value toggle for a single noun. The shipped precedent says ROUTIQ's current position is not a gap to close; it is the industry norm.

The generalisation that organises the whole survey, and the single most useful sentence in this document:

> **Anything the engine computes with is an enum in code. Anything it merely displays or groups by is a user-owned row. The two are joined by one or two boolean marker flags on the row.**

Fleetio's `Issue.state` drives resolution semantics, so it is a hardcoded enum; `VehicleStatus` drives nothing, so it is full CRUD with `name`, `color`, `position` and nothing else. Odoo's `account.move.state` drives posting, so it is a `Selection`; `crm.stage` drives a kanban column, so it is a table. Both products independently landed on a marker flag as the bridge — Fleetio's `WorkOrderStatus.completed` ("Whether Work Orders will be set to `completed` when they are moved to this status") and Odoo's `crm.stage.is_won`.

### Recommendations, ranked by fit for two tenants growing to tens

**1. Promote the seed bundles to a real provisioning command.** This is the highest-value, lowest-cost item and it is a live defect, not a design question. `presetCategories()` and `defaultApprovalRules()` exist and are correct, but `grep` finds them called only from `apps/api/src/test/seed.ts`. There is no production path that creates a workspace. Onboarding tenant #3 today means running test code or hand-writing SQL. AWS states onboarding as a design principle — "Even when onboarding is an internally executed process, **it should still automate all the elements of tenant creation**" ([SaaS Lens, OPS 3](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/operate.html)) — and Microsoft's guidance for exactly ROUTIQ's scale is that you may skip the control plane but not the process: "This approach might work if your system has fewer than 10 tenants… **However, you should still have a process and maintain a central location to track your tenants and their configurations**" ([Azure, control planes](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/control-planes)). Make it `provision-workspace.v1` through the existing dispatcher so the seed inherits idempotency, audit and `created_by_command_id` for free.

**2. Add a seed-origin side table, not a column.** Odoo's `ir.model.data` exists for precisely this, and its class docstring is the clearest statement of the requirement found anywhere: it "allows tracking the origin of data installed by Odoo modules themselves, **thus making it possible to later update them seamlessly**" ([`ir_model.py`](https://github.com/odoo/odoo/blob/18.0/odoo/addons/base/models/ir_model.py)). Keep it as `(bundle_code, bundle_version, seed_key) → (table_name, row_id)` with a unique index on the key pair. Business tables stay clean; replay becomes idempotent; the bundle version is recorded per row. ROUTIQ gets ServiceNow's cleverest trick for free here: ServiceNow marks the *customer's edits* rather than the vendor's rows, so absence of a marker means "still baseline" and cost scales with edits rather than with shipped rows ([Revert a customization](https://www.servicenow.com/docs/r/zurich/platform-administration/upgrade-center/uc-revert-customization.html)). ROUTIQ already writes that marker — a seeded row whose `created_by_command_id` points at a later command is, by definition, a row the tenant has touched.

**3. Make categories editable at runtime through commands — add, rename, deactivate; never delete.** The `categories` table is already per-workspace with `labelFr`/`labelEn` and a `(workspace_id, kind, code)` unique index. It is 90% of a terminology system and it is currently seed-only. This is the highest expressiveness-per-line change available, and it is where the vertical products put nearly all their per-customer variance: Fleetio's Vehicle Types and Service Tasks, ServiceTitan's Trades and Divisions ("You can create your own custom trades and divisions"), Odoo's `fleet.vehicle.state`. Two constraints from the survey are non-negotiable. Deactivate, never delete — Fleetio archives standard Service Tasks rather than deleting them, and Odoo's `fleet_vehicle.py` has to write `self.env.ref('fleet.fleet_vehicle_state_waiting_list', raise_if_not_found=False)` because a customer may have deleted a row its code depends on. And never key handler logic on a seeded row's identity; key it on `code` or on a marker flag, which is why Fleetio's boolean is strictly the better design.

**4. Keep approvals as the rules table. If the pilot demands chains, add `step_order` — never a graph.** The existing specificity-ranked table in `approvals.ts` is exactly the shape the most mature products in the category use. Salesforce's `ApprovalProcess` metadata is an **ordered array** of `ApprovalStep`, each with its own entry criteria and `assignedApprover` — declarative nested metadata, no graph ([Metadata API](https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_approvalprocess.htm)). SAP's release strategy is characteristic-matching plus up to eight ordered release codes. Ramp's spend policies are conditions on amount and role resolving to a small closed set of outcomes. Odoo — which has an arbitrary code-execution escape hatch available — still models approvals as an ordered numbered list of role-scoped steps. The dividing line the products themselves draw: **fixed known states with only routing varying gets a rules table; customer-authored unbounded states gets a graph.** Jira needs a graph because its states are customer-authored. ROUTIQ's are not.

**5. Extend the pull-queue handoff pattern rather than building routing.** `pendingApprovalConditions()` — SUBMITTED entries within the caller's branch scope — is the whole handoff mechanism today, and it is the right primitive. It is pull-based, needs no assignment table, and degrades correctly offline because the queue is a read. The lead's question asked about "role-to-role handoffs, status flows for how data moves person to person"; the answer from the survey is that this is a status column plus a scope-filtered read, and every product in the category implements it that way. When a second record type needs a queue, copy the predicate function pattern, not a routing engine.

**6. Move template field lists from code to data only when a third tenant forces it.** `TEMPLATES` in `commands/templates.ts` is a hardcoded const, so a tenant with a different required-field list needs a deploy. The evidence supports fixing this eventually — ServiceTitan's job type carries its own required-field set, which is the single highest-leverage idea in the survey for trucking-versus-passenger variance. But it is rung three of the ladder (§7) and the trigger has not fired. When it does, keep the type system tiny: Fleetio ships four field types (`checkbox`, `date`, `dropdown`, `text`), ServiceTitan three. Fifteen means you have become a platform.

Two things ROUTIQ already does that the research validates and that should be defended in review: stamping `template_code` + version on every record (Samsara pins every form submission to an immutable `revisionId` for the same reason — without it, history silently reinterprets itself), and treating module flags as data checked once in the pipeline (AWS: "**even if a single tenant needs a unique feature—that feature should be introduced as a customization to the core platform**").

## Where ROUTIQ actually stands

Verified against the code on 2026-07-29, because the answer to "what should we build" depends on what exists.

| Lever | Location | State |
|---|---|---|
| Module flags | `workspaceModules` (`schema.ts:204`), `module-toggle.ts` | Working, enforced once in the pipeline |
| Categories with bilingual labels | `categories` (`schema.ts:290`), unique on `(workspace_id, kind, code)`, `labelFr`/`labelEn` | Per-workspace rows, but **no add/rename command** — seed-only |
| Category seed bundle | `commands/category-presets.ts` | Hardcoded array, **called only from `src/test/seed.ts`** |
| Approval rules | `approval_rules` (`schema.ts:223`), `approvals.ts` | Working. Specificity-ranked; most-specific match wins; single step |

The gaps that matter: there is no production provisioning path, categories are immutable at runtime, and template field lists require a deploy. Terminology renaming of the fixed nouns and multi-step approval chains are *absent by design* and the research says leave them absent.

## 1. Metadata-driven architecture, and why it is wrong here

Salesforce's own technical brief states the mechanism plainly: "When you create a new application object… the platform does not create an actual table in a database or compile any code. Instead, the platform simply stores some metadata that it can then use at runtime to dynamically materialize virtual application components" ([Platform Multitenant Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-multitenant-architecture.html), Bobrowski & Leddy; the live URL 403s to automated fetch and was read via the Wayback Machine, as was the [2008 whitepaper](https://web.archive.org/web/2012/https://www.developerforce.com/media/ForcedotcomBookLibrary/Force.com_Multitenancy_WP_101508.pdf)).

Physically it is a handful of very wide tables. `MT_Objects` holds one row per tenant-defined object, `MT_Fields` one per field, and `MT_Data` is the universal data table with `Value0…ValueN` flex columns — "All flex columns use a variable-length string data type so that they can store any structured type of application data."

The cost follows directly from that sentence. Untyped shared string columns cannot be indexed, so indexes, uniqueness and foreign keys are all re-implemented as denormalised pivot tables maintained synchronously on write: `MT_Indexes` ("it is not practical to create native database indexes for the flex columns of MT_Data… Instead, the platform manages an index of MT_Data by synchronously copying field data marked for indexing to an appropriate column in an MT_Indexes pivot table"), `MT_Unique_Indexes`, `MT_Relationships`, `MT_Fallback_Indexes`, `MT_Name_Denorm`.

**What had to be built around the kernel is the real argument.** Salesforce runs a second application-level query optimizer, because — in their own words — "The Salesforce multitenant architecture uses the underlying database in such a way that the database system's optimizer can't effectively optimize search queries" ([Large Data Volumes best practices](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_large_data_volumes_bp.pdf)). It runs a parallel statistics system on a nightly cycle, because "the platform must keep its own set of statistical information to help the database understand the best way to access the data." It runs pre-queries before every real query. It has skinny tables, a separate external search engine with ~15 minutes of index lag, and a governor regime strict enough that "Submitted unit tests must cover no less than 75 percent of the application's source code" before you may deploy.

The customer-facing costs are documented and severe: 100 SOQL queries and 150 DML statements per synchronous transaction, 6 MB heap, 10,000 ms CPU ([Limits Quick Reference](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf)); custom indexes stop being used above a selectivity threshold that "maxes out at 333,333 targeted records" ([Maximizing SOQL performance](https://developer.salesforce.com/blogs/engineering/2013/07/maximizing-the-performance-of-force-com-soql-reports-and-list-views)); and "As a customer, you also cannot optimize the SQL underlying many application operations because it is generated by the system, not written by each tenant."

The economics are stated by Salesforce itself, and the target is explicit: the architecture had to answer "how will the application's response time scale as **tens of thousands of tenants** subscribe to the service?" The 2008 whitepaper cites "some 47,000+ organizations." (The SIGMOD 2009 paper's "55,000+" figure reached the researcher only through an indexed abstract; [the paper](https://dl.acm.org/doi/10.1145/1559845.1559942) is paywalled and ACM returned 403. Treat it as second-hand.)

No Salesforce document says "don't do this below N tenants" — that inference is ours. But the trade is unambiguous. The entire apparatus buys one thing: amortising a single physical schema and a single upgrade event across tens of thousands of tenants with no per-tenant DDL. Below that scale you pay the whole fixed cost and get none of the amortisation, when the alternative is real columns, real indexes, a planner that tells the truth, and one migration per schema change.

**ServiceNow is the proof that the two halves are separable, and it is the more relevant model.** ServiceNow is at least as metadata-driven at the application layer — `sys_db_object`, `sys_dictionary` and `sys_documentation` define every table, column and label — but it keeps the physical layer honest with real typed columns and a "**dedicated database for each customer instance**," explicitly rejecting the shared-column approach: this boundary "is not dependent on data separation approaches commonly used by many SaaS providers, **such as tagging data in shared databases**" ([Securing the ServiceNow AI Platform](https://www.servicenow.com/content/dam/servicenow-assets/public/en-us/doc-type/resource-center/ebook/ebk-how-servicenow-delivers-safe-and-secure-cloud-services.pdf)). Its limits are the database's own, surfaced honestly — a 1,000-column and 64 KB row ceiling from InnoDB ([KB0723580](https://support.servicenow.com/kb?id=kb_article_view&sysparm_article=KB0723580)) — rather than an invented governor layer.

The lesson for ROUTIQ: **a dictionary-driven application does not require a universal data table.** ROUTIQ's `custom_values` JSONB validated per template is the cheap version of the same idea, and Postgres will actually plan queries against the real columns around it.

Worth noting what Salesforce tells its own builders. The recommended configuration vehicle is Custom Metadata Types, whose stated use cases are narrow and configuration-shaped — mappings, business rules, reference data — not domain modelling. And their architecture guidance is blunt: "**No customizations are trivial.** Over time, every change has consequences" ([Well-Architected: Intentional](https://architect.salesforce.com/well-architected/easy/intentional)).

## 2. Config-as-data versus workflow engines

**No vendor or author states a threshold in terms of rule count or variance.** Every stated threshold is about durability, long-running state, cross-service coordination and failure compensation. That absence is the finding.

AWS is the most usable. Use application code when "Your application logic is primarily within Lambda functions" and "You want fine-grained control over execution state in code"; use Step Functions when "You need visual workflow representation for cross-team visibility," "You're orchestrating multiple AWS services," or "Non-technical stakeholders need to understand and validate workflow logic" ([Durable functions or Step Functions](https://docs.aws.amazon.com/lambda/latest/dg/durable-step-functions.html)). Note that none of the engine criteria is "the logic is complicated." Their staged advice: "**Starting simple, evolving complex**: Begin with durable functions for Lambda-centric workflows. Add Step Functions when you need multi-service orchestration."

Camunda's own replacement trigger is a maintenance-cost threshold, not a complexity one: replace homegrown workflow when "engineers spend more time on workflow infrastructure than on the business logic that runs on it," "In-flight cases break on every deploy," or "Process state lives in logs, scattered tables, and tribal knowledge" ([Replace Homegrown Workflows](https://camunda.com/platform/use-cases/replace-homegrown-workflows/)). **ROUTIQ's process state lives in a versioned table and deploys do not strand in-flight work, so Camunda's own stated trigger has not fired.**

The operational cost is concrete. Camunda 8 Self-Managed needs Zeebe brokers and gateways, Operate, Tasklist, Connectors, Optimize, Identity backed by Keycloak, and Web Modeler backed by PostgreSQL; the production guide requires provisioning Aurora PostgreSQL, OpenSearch, an OIDC directory, an OpenSearch snapshot repository and an S3 bucket for broker backups before you deploy ([Helm production guide](https://docs.camunda.io/docs/8.7/self-managed/operational-guides/production-guide/helm-chart-production-guide/)), with volumes needing "an absolute minimum of 1,000 IOPS" and network storage unsupported. Temporal needs a four-service server, Cassandra/MySQL/PostgreSQL persistence, Elasticsearch for production visibility, your own worker fleet, and a permanent determinism tax on every developer — all workflow code "must be deterministic to support replay" ([Workflow Definition](https://docs.temporal.io/workflow-definition)). For an on-prem appliance that must run cold from one `docker-compose.yml` (§6a), this is disqualifying on its own.

**On who edits the rules, the three most authoritative sources agree and all three are pessimistic.** Fowler on the business-users-configure-it pitch: "As so often, this can sound plausible but rarely works out in practice" ([RulesEngine](https://martinfowler.com/bliki/RulesEngine.html)). His positive recommendation: "The sweet spot, however is in making DSLs business-readable rather than **business-writeable**" ([BusinessReadableDSL](https://martinfowler.com/bliki/BusinessReadableDSL.html)). Hohpe: "Just converting something into a diagram doesn't immediately make it suitable for non-programmers" ([The Quest for Low-Code](https://architectelevator.com/architecture/low-code-no-code/)). If engineers edit the rules either way, the engine's headline benefit is already gone.

Fowler's defence of the simple alternative is direct — "there's a lot to be said for avoiding rules engine products," in favour of "a more domain specific approach to rules, where a team builds a limited rules engine that's only designed to work within that narrow context." ROUTIQ's `evaluateApproval` is exactly that. His scaling warning is worth pinning to the table: "Any system with enough rules to need sophisticated algorithms probably has too many rules to be understood." And his named failure mode is rule *interaction*, particularly chaining — "it was easy to set up a rules system, but very hard to maintain it because nobody can understand this implicit program flow." ROUTIQ's specificity ranking with a most-specific-wins resolution avoids this; the day a rule's output becomes another rule's input, the warning applies.

**The failure mode of adopting an engine too early is documented by the engine vendor's own co-founder.** Bernd Ruecker's "7 sins of workflow," drawn from fifteen years of Camunda projects, lists: no engine, **wrong engine**, homegrown engine, **zero-code suite without developer support**, **granularity bloopers**, stakeholder habitat violation, **over-engineering** ([slides](https://www.slideshare.net/BerndRuecker/the-7-sins-of-workflow); the [blog original](https://blog.bernd-ruecker.com/the-7-sins-of-workflow-b3641736bf5c) blocks automated fetch). Four of seven are failure modes of *adopting* an engine. Sin four is the specific trap: you buy the engine so business users can configure it, discover they cannot, and now your developers write business logic into a properties panel with no IDE, no type checking, no diff and no test harness.

**The origin stories of the two best-known engines are worth knowing, because neither is about approval variance.** Uber built Cadence because config-as-data ran out at their scale: "Traditionally, workflows have been written with DSLs or configs defining the order and dependencies between tasks," which "limited how much users could do with workflows or made DSLs and configs overly complicated over time" ([Cadence overview](https://www.uber.com/us/en/blog/open-source-orchestration-tool-cadence-overview/)). Note their conclusion — "simplicity should be on the workflow writing side rather than the orchestration" — is a vote for workflows as *ordinary code*, not for a visual graph, and the scale that triggered it was "over a thousand services at Uber." Netflix Conductor is likewise scale-driven, built for orchestration across services with "control and visibility into their interactions" ([Netflix Tech Blog](https://netflixtechblog.com/netflix-conductor-a-microservices-orchestrator-2e8d4771bf40)). **Both engines were built for cross-service coordination at hundreds-to-thousands-of-services scale. Neither was built because approval rules got complicated.**

Three conditions make config-as-data defensible rather than the config anti-pattern Hohpe criticises. Treat the rules table as code — versioned, reviewed, tested (his complaint is that configuration "often lacks the same safety nets… syntax highlighting, editor support, version control, code reviews, and automated tests"; "If changing settings can break your application, you better consider that coding"). Keep the rules flat and non-chaining. And aim for business-readable, not business-writeable.

Two gaps, stated so they are not over-claimed. **Temporal publishes no "when not to use Temporal" guidance** — both [Understanding Temporal](https://docs.temporal.io/evaluate/understanding-temporal) and the use-cases page are purely affirmative, so the negative case must be built from operational requirements. And **Camunda argues the opposite** of "a simple state machine suffices": "If you now try to rely on workflow languages that promise to be simpler than BPMN, what it really means is that they lack important workflow patterns" ([Workflow patterns](https://docs.camunda.io/docs/components/concepts/workflow-patterns/)).

## 3. Inner-platform effect and the second-system trap

A correction to a common assumption first: **the c2 wiki has no `InnerPlatformEffect` page and no `SoftCoding` page.** The complete c2 page index ([names.txt](https://wiki.c2.com/names.txt), 36,852 entries) contains neither. The origin is exclusively Alex Papadimoulis.

The original definition, from [The Inner-Platform Effect](https://thedailywtf.com/articles/The_Inner-Platform_Effect) (2006-04-21):

> "The Inner-Platform Effect is a result of designing a system to be so customizable that it ends becoming a poor replica of the platform it was designed with. This 'customization' of this dynamic inner-platform becomes so complicated that only a programmer (and not the end user) is able to modify it."

The second sentence is load-bearing. The failure is not that the meta-system is ugly; it is that **the promised end-user configurability never materialises**. His worked example is a "Data Structure Modeler" storing tables, fields, datatypes and values as rows, and the closing line is the whole argument: "Ironically, Mario was brought into the system because the client wanted to add a new Field to a form."

[Soft Coding](https://thedailywtf.com/articles/Soft_Coding) (2007) adds the diagnosis — "The reason we find ourselves Soft Coding is because we fear change" — and, in its Enterprise Rules Engine example, describes a `Fields/Atoms/AtomSets/AtomGroups/AtomGroupSets` schema where "in order to implement a simple rule… a developer must add or update anywhere between ten and thirty rows in the database."

**Mike Hadlow's [Configuration Complexity Clock](https://mikehadlow.blogspot.com/2012/05/configuration-complexity-clock.html) (2012) is the single most useful essay for this decision.** Its stages, in his words:

- **12 (midnight), hardcoded** — "a simple new requirement which we quickly code up as a little application… we've hard-coded all the application's values."
- **2, config file** — "some of the business values change, so we find ourselves rebuilding and re-deploying it just to change a few numbers."
- **4–5, structured config** — "appsettings are no longer sufficient, we have groups of values and hierarchies of values."
- **6, rules engine** — "The configuration moves from its XML file into a database and has its own specialised GUI. **Initially there was hope that non-technical business users would be able to use the GUI to configure the application, but that turned out to be a false hope; the mapping of business rules into the engine requires a level of expertise that only some members of the development team possess.**"
- **9, DSL** — "The team stops work for several months to implement the DSL," after which "Debugging the DSL code is difficult, there's little tooling support."
- **Back to 12** — "we're back where we started four years ago, hard coding everything, except now in a much crappier language."

His thesis: "At a certain level of complexity, hard-coding a solution may be the least evil option." His test: "You already have a general purpose programming language, before you go down the route of building a business rules engine or a DSL… consider that with a slicker build-test-deploy cycle, it might be far simpler just to hard code it." He is not absolutist — "I would jump at the chance of building a DSL given the right requirements" — and he notes "I've never seen an organisation go all the way around the clock, but I've seen plenty that have got to 5, 6, or 7 and feel considerable pain."

**The convergence is the striking part.** Papadimoulis (2006), Fowler (2008/09) and Hadlow (2012) independently report the same empirical failure: the business-user-configures-it promise never lands, the config surface ends up operated only by developers, and those developers are then working in a worse language than the one they started with.

Brooks on the second system, read from the [Internet Archive full text](https://archive.org/stream/MythicalManMonth/Brooks%201974%20The%20Mythical%20Man-Month-%20Essays%20on%20Software%20Engineering,%20Anniversary%20Edition%20(2nd%20Edition)_djvu.txt) of the anniversary edition: "**This second is the most dangerous system a man ever designs**… The general tendency is to over-design the second system, using all the ideas and frills that were cautiously sidetracked on the first one." His reason the *third* system is safer is itself a rule of three about generalisation — only after three do you learn which parts of experience are "particular and not generalizable." He also names a second failure directly relevant to a config engine built for last year's variability model: "a tendency to refine techniques whose very existence has been made obsolete by changes in basic system assumptions."

Ousterhout's position on configuration parameters, from his own Stanford CS 190 notes (the book is not freely available and was not pirated): "Minimize 'voodoo constants' (configuration parameters) — **If you don't know the right value, how will a user or administrator ever figure it out?**" ([modular design](https://web.stanford.edu/~ouster/cgi-bin/cs190-spring16/lecture.php?topic=modularDesign)), sitting inside "Let a few module developers suffer, rather than thousands of users." A configuration parameter is an unsolved design problem exported to someone with strictly less information than you. His generality advice is precise and often misquoted: "**My advice: make classes somewhat generic:** Overall capabilities reflect current needs / Design an interface that is generic enough to be used for other purposes besides today's needs" ([winter18](https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=modularDesign)). The generality is in the **interface**; the implementation stays scoped to today. That is the exact inverse of an inner platform, which generalises the implementation while the interface degenerates.

Fowler's [Yagni](https://martinfowler.com/bliki/Yagni.html) extends explicitly to parameterisation: "the same argument applies for abstractions to support future flexibility… **Yagni says not to do this**… any abstraction that makes it harder to understand the code for current requirements is presumed guilty." Four costs: build, delay, **carry** ("this complexity makes it harder to modify and debug that software, thus increasing the cost of other features"), repair. But note the exception, which is almost exactly the i18n case: "add something that's easy to do now, adds minimal complexity, yet significantly reduces the later cost. **Using lookup tables for error messages rather than inline literals are an example.**"

And the rule of three, in its harsher reuse form ([c2 RuleOfThree](https://wiki.c2.com/?RuleOfThree), citing Biggerstaff and Richter): "You must have looked at at least three systems to understand what is common across them… **It takes three times as much effort to make something reusable as to make it usable**… You will receive payback after the third release."

The most explicit "when" list in the canon is [c2 PrematureGeneralization](https://wiki.c2.com/?PrematureGeneralization), which ranks three timings: generalise by refactoring with the code already in hand, which "guarantees that the generalization will be useful"; generalise when you *know* you will need it within days; or generalise when you merely *think* so, which "paves the way for a possibly inappropriate generalization." Its symptom list reads as a configurability checklist — "A function parameter which is always given the same value / An abstract class with only one descendant / A library which is used by only one program." And the sharpest formulation of the whole question: "'Premature' has to do with when, not what. **It is premature to posit a generalization until you can base it on concrete solutions to real problems.**"

The canon does not oppose generality. It opposes generality chosen before you have the evidence to shape it — and it insists the evidence come from three concrete existing cases. ROUTIQ has two.

## 4. AWS SaaS Factory and first-party cloud guidance

AWS and Microsoft agree on the invariant, and it is the one rule to carry forward: **per-tenant variation is a data attribute evaluated at runtime, never a code branch or a forked deployment.**

AWS's SaaS OPS 4 is the whole argument, and it is worth quoting at length because it names the temptation and the compromise ([SaaS Lens, Operate](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/operate.html)):

> "As each new custom environment is introduced, **a SaaS organization slowly makes its way to a traditional software model.**"

> "The challenge, then, is to find a strategy that allows you to meet these occasional one-off needs **without creating a forked version of your product**… instead of spinning off a separate version, you'd invest the extra time and effort into figuring out how these new features can be added in a way that makes them available to *all* customers. Then, **through tenant configuration, you can determine which tenants will have these new capabilities enabled**."

> "The key takeaway here is that—**even if a single tenant needs a unique feature—that feature should be introduced as a customization to the core platform.**"

The counterweight matters as much as the rule: "**If, by introducing feature flags, you create a complex maze of options that end up presenting every tenant a unique experience, your system will quickly become unmanageable.** Try to be selective… the business should not see this as a sales tool that enables the organization to offer one-off customizations to new customers." ROUTIQ's fixed module registry in code, rather than arbitrary flags, is the right expression of this.

On the tenant record itself, AWS's most concrete shape is from the [tenant onboarding best practices post](https://aws.amazon.com/blogs/apn/tenant-onboarding-best-practices-in-saas-with-the-aws-well-architected-saas-lens/): the tenant management service "creates the unique tenant id… and stores the tenant-specific details (**tenant id, organization data, tier information, tenant settings and environment details**)." At runtime, tenant context is bound into the identity token rather than looked up: "tenant context needs to become a first-class construct that can be resolved and easily accessed by the layers of your application **without invoking another service**" ([general design principles](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/general-design-principles.html)). ROUTIQ already does this — auth resolves workspace, role and branch scope server-side, and the envelope never accepts them from the client.

Microsoft enumerates the customisation approaches with tradeoffs, and names the antipattern outright ([deployment and configuration](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/deployment-configuration)):

> "**Specialized customizations for tenants:** Avoid deploying features or a configuration that only applies to a single tenant. **This approach adds complexity to your deployments and testing processes.** Instead, use the same resource types and codebase for each tenant."

Their distinction between *temporary/progressive* variation and *permanent commercial* variation is a genuinely useful one ROUTIQ has not made explicitly: feature flags are for rollout, while "Sometimes you must selectively enable specific features for specific customers… **Feature flags aren't usually the right choice for these scenarios.** Instead, consider building a process to track and enforce the *license entitlements* that each customer has." ROUTIQ's `workspace_modules` is an entitlement table, not a flag table, which is the correct reading.

The maintenance warning, quoted directly: "**Custom integrations for specific tenants can make your solution harder to test and harder to modify in the future because you have to understand more code paths**" ([tenant integration](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/integration)). And a warning against the tempting escape hatch: "**Be careful about enabling tenants to initiate their own updates. This process is complex to implement, and it requires significant development and testing effort to deliver and maintain**" ([updates](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/updates)).

**On small tenant counts, Microsoft addresses it directly and AWS does not — and that absence is itself a finding.** Microsoft's framing of tenant list as *configuration* versus *data* is the most directly applicable paragraph found in the entire research: the configuration approach "works well for small numbers of tenants… as the number of tenants increases, **often around 10 or more**, it becomes cumbersome," while the data approach "is often much more time-consuming to build. Your effort needs to be justified by the number of tenants." Elsewhere they give the explicit carve-out quoted in the summary: fewer than 10 tenants means manual operations are acceptable, but you still need a documented process and a central place tracking tenants and their configurations, because "**If you need to automate processes in the future, your documentation and scripts can form the basis of your control plane.**"

AWS has no small-N carve-out anywhere the researcher could find; its framing is uniformly growth-oriented. Practically: AWS's config-not-code invariant transfers cleanly to a two-tenant pilot, but its onboarding and control-plane machinery is sized for hundreds of tenants and should not be read as a mandate at ROUTIQ's scale.

One gap worth naming, because it shapes what ROUTIQ has to design itself: **no first-party cloud page names a "seed the tenant with a business-configuration template" pattern.** AWS's and Google's "baseline" concepts are infrastructure-shaped. Seeding categories, approval defaults and required-field lists is designing past the published guidance, not against it. (Also note that [SaaS Architecture Fundamentals](https://docs.aws.amazon.com/whitepapers/latest/saas-architecture-fundamentals/control-plane-vs.-application-plane.html) is banner-marked "for historical reference only"; the SaaS Lens and the 2025-revised Microsoft pages are the maintained sources.)

## 5. Per-tenant terminology

Six vendors, five distinct mechanisms. The short answer for ROUTIQ is that **the general mechanism is cheap and well-understood, and you should still not build it yet** — but the two rules that prevent it from being a disaster should be adopted now, because they are about identifiers, not about renaming.

### The mechanism, where it exists

**Salesforce is the canonical example and has the most honest documentation.** The structurally important fact: **renaming and translating are the same operation.** The rename wizard opens with a language selector and closes with "Repeat this procedure to translate labels into all other languages used in your organization" ([Rename Tabs and Labels](https://help.salesforce.com/s/articleView?id=platform.customize_rename.htm&language=en_US&type=5)). A rename is a write into the (label, language) catalogue for one language. That is exactly the model a French-first product wants: renaming "Asset" to "Vehicle" in `en` and "Actif" to "Véhicule" in `fr` are two independent writes, not one rename plus a translation. **ROUTIQ's `labelFr`/`labelEn` columns on `categories` are already this shape.**

Salesforce also captures grammatical metadata rather than a bare string — singular and plural are separate inputs, plus "select **Starts with a vowel sound** for labels that start with a vowel to ensure that Salesforce uses the proper article." The underlying `CustomObjectTranslation` metadata carries `caseValues` for nominative/accusative/dative/genitive plus `gender` and `startsWith`.

**ServiceNow stores labels as ordinary rows** in `sys_documentation`, keyed `(table, element, language)` with `Label`, `Plural` and `Hint` columns, and the admin gesture is insert rather than update — "Selecting Insert creates a new record in the Field Label [sys_documentation] table for this field label in the selected language" ([Translate a field label](https://www.servicenow.com/docs/r/platform-administration/system-localization/t_TranslateAFieldLabel.html)). Its fallback chain is the one ROUTIQ wants: "Setting fallback languages creates a **three-level hierarchy** in which an intermediate language is used before defaulting to English… you would need to provide custom translations of UI strings in Mexican Spanish only when the translation differs from the Spanish translation" ([Set a fallback language](https://www.servicenow.com/docs/r/platform-administration/system-localization/set-fallback-language.html)) — structurally identical to fr-CM → fr → en. Note though that ServiceNow's label table is **instance-wide and explicitly not domain-separable** ([Domain separation terms](https://www.servicenow.com/docs/r/platform-security/bp-terms-conditions.html)); an MSP wanting per-customer nouns must run separate instances.

**Zendesk never renames anything.** It stores a placeholder where the string would be and resolves it per viewer: "Dynamic content is a combination of a default version of some text and variants of the text in other languages… represented by a placeholder such as `{{dc.my_placeholder}}`" ([API reference](https://developer.zendesk.com/api-reference/ticketing/ticket-management/dynamic_content/)). The best single design detail in the whole survey is its `title`/`raw_title` pair — every localisable property is stored twice, resolved and unresolved, and "**If dynamic content is not used for the property, the two values are identical.**" One write path to the displayed string, which is why Zendesk has no equivalent of Jira's shadowing bug.

**HubSpot renames standard objects on all plans**, with singular and plural as separate inputs and the key constraint stated plainly: "**The internal name used by integrations and APIs will not change**" ([Rename objects](https://knowledge.hubspot.com/object-settings/rename-objects)). Their sharpest design choice: "**For users editing property labels or options within HubSpot, translated values will not be visible.**" Read paths localise; write paths always show the base string, so an admin can never accidentally edit through the translation layer.

### The warnings, which are the actually valuable part

Vendors are unusually honest in admin docs, and four failure classes recur.

**Setup and help surfaces keep the original names.** Salesforce: "Salesforce Help and most pages in Setup always display the original names for standard objects, fields, and tabs." HubSpot: "there are some areas in your account on desktop where the default name may still appear" — they even have to disclaim their own documentation. Salesforce's remedy for stale help is not to fix it but to let you replace Salesforce Help with your own URL entirely.

**Derived artifacts do not follow the rename.** Salesforce lists list views, report names, email templates, page layouts and record types as things you must update by hand.

**Name-as-key breaks queries silently — this is the important one.** Jira: "**JQL looks for issue types according to their name.** If an administrator renames an issue type at the Level 1 hierarchy, the query in your filter no longer matches" ([KB](https://support.atlassian.com/jira/kb/filters-break-after-renaming-issue-types-at-the-epic-level/)). Empty result set, not an error. Jobber has the same defect in its templates: "As long as the name of a product or service remains unchanged in a quote template, it stays connected."

**Two write paths to one string produce shadowing.** Jira's most instructive bug: rename an issue type and the old name still appears on the create screen, because "**You'll notice a translation added to the affected issue type which consists of the old issue type name**" ([KB](https://support.atlassian.com/jira/kb/after-renaming-existing-issue-type-old-issue-name-is-still-shown-on-the-issue-create-drop-down-menu/)). Renaming the base row does not invalidate the override rows layered on top.

### The standard technical pattern

Well-documented at the library layer, and if ROUTIQ ever needs it the implementation is small. i18next's `fallbackNS` is the override primitive: "if a key to translate isn't found in the given namespace, it will look it up in the indicated fallbacks" ([principles/fallback](https://www.i18next.com/principles/fallback)). `defaultNS: 'tenant'` plus `fallbackNS: 'base'` gives per-key tenant override with no change at call sites. For eager merging, `addResourceBundle(lng, ns, resources, deep, overwrite)` with both booleans true is the documented one-call layering ([API](https://www.i18next.com/overview/api)). Two traps: set `returnEmptyString: false` or an empty override string wins over the base, and `cloneInstance` shares the resource store, so per-tenant isolation needs `forkResourceStore: true`. Note also that `i18next-chained-backend` is a loader, not a merger — it reads "until a backend returns some resources," first-hit-wins over the whole namespace.

Rails states the pattern most plainly: chain backends so you "use standard translations with a Simple backend but store custom application translations in a database" ([guides](https://guides.rubyonrails.org/i18n.html)). ICU gives the conceptual model — a sparse override layer where "Data that is already the same on the more general level is not repeated," resolved most-specific-first with "At any point, if the desired data is found, then the fallback procedure stops." A tenant override layer is structurally identical to a locale variant: `fr_CM_acme` → `fr_CM` → `fr`.

One French-specific caution. Mozilla Fluent is the only surveyed design that survives an inflected language, because its **terms** carry grammatical metadata — `-brand-name = Aurora` with `.gender = feminine`, and case-parameterised variants ([Fluent guide](https://projectfluent.org/fluent/guide/terms.html)). For a fr-CM product this is not a nicety: swapping "véhicule" (m.) for "remorque" (f.) breaks article and adjective agreement everywhere downstream unless the term carries its gender. Salesforce reached a weaker version of the same conclusion independently.

**Negative finding:** no first-party SaaS engineering blog post on implementing per-tenant terminology overrides could be found. Shopify, Slack and GitLab all have first-party i18n writing; none covers tenant overrides. The pattern lives in library docs and admin guides, never as a case study.

### What ROUTIQ should take from this now

Not the override layer. Two rules, both about identifiers, both worth applying immediately since categories are about to become editable:

- **Separate the display name from the identifier and never key on the display name.** `categories.code` is the identifier and must be immutable once written; `labelFr`/`labelEn` are free to change. This is the rule Jira violated and everyone else follows — Pipedrive's 40-character hashes, HubSpot's internal names, Salesforce's API names, Odoo Studio's "a field's technical name cannot be changed."
- **Pin the invariant string for machine consumers.** Zendesk's "Notify URL target action always uses the default variant" and Atlassian's "There are no changes to existing APIs; they will continue to function as usual with the term 'issue'" are the same decision. Command payloads, audit events, CSV exports and offline envelopes carry `code`; only rendered UI carries the label.

## 6. Starter packs and seed-bundle onboarding

**Odoo is the only vendor examined that ships configuration as ordinary rows in ordinary business tables with a documented per-record flag governing re-apply.** Everyone else either copies opaquely and never looks back, or had to invent a parallel universe to make it work.

Odoo states the thesis directly: "Odoo is greatly data-driven, and a big part of modules definition is thus the definition of the various records it manages: UI (menus and views), security (access rights and record rules), reports and plain data are all defined via records" ([Data Files](https://www.odoo.com/documentation/18.0/developer/reference/backend/data.html)). Bundles are CSV or XML in a module; the manifest separates `data` ("must always be installed or updated with the module") from `demo`.

**The upgrade answer is `noupdate`, and its semantics are exactly what ROUTIQ needs to decide.** From the same page, the code sample's own comments:

```xml
<odoo>
  <data noupdate="1">
    <!-- Only loaded when installing the module (odoo-bin -i module) -->
  </data>
  <!-- (Re)Loaded at install and update (odoo-bin -i/-u) -->
</odoo>
```

So the default is overwrite on every upgrade — a tenant's edit to a non-`noupdate` seeded record is silently reverted — and `noupdate="1"` means "seed once, then never touch it again." The flag is stored **per record**, in `ir.model.data`, and enforced by one line in `_load_records`: `if not (update and d_noupdate): to_update.append(data)`. A companion flag, `forcecreate` (default true), means a `noupdate` record the tenant deleted *is* recreated.

The localisation modules are the canonical seed pack, and two details land directly on ROUTIQ's constraints. **Translations ride inline in the seed CSV** via a per-locale column suffix — the Lithuanian chart of accounts is `"id","name","code","account_type",…,"name@lt"`, and `chart_template.py` documents that "The data can contain translation values (i.e. `name@fr_FR`…)". And **template records and tenant records are distinct, with instantiated rows getting per-tenant stable keys**: "An xml_id that doesn't contain a `.` will be treated as being linked to `account` and prefixed with the company's id (i.e. `cash` is interpreted as `account.1_cash`…)." That is precisely the shape ROUTIQ wants — one shared bundle definition, per-tenant materialisation, keys of the form `<bundle>.<workspace_id>_<seed_key>`.

Odoo's industry packs are *defined* by the absence of code: "An Industry module is a suite of applications, configurations, and data that fit a specific business… **It does not contain Python code and can be installed in SaaS databases**" ([Odoo 17 release notes](https://www.odoo.com/odoo-17-release-notes)). And the strongest first-party statement that seeding-as-data beats a configuration engine comes from Odoo in the shadow of their own config engine: "**Whilst a lot is possible with Studio, it is also possible to define models, fields and logic in XML Data Files. This makes it easier to develop, maintain and deploy these customizations**" ([Write importable modules](https://www.odoo.com/documentation/19.0/developer/tutorials/importable_modules.html)). Studio's own export format is a data pack, and its export wizard exposes `noupdate` to end users as an "Updatable" checkbox.

**Salesforce is the cautionary contrast.** Their packaging layer structurally cannot carry data rows — "when apps with custom objects and custom settings are deployed, the metadata of those objects (the header) get deployed, but **the records are left behind**" ([Introducing custom metadata types](https://developer.salesforce.com/blogs/engineering/2015/04/custom-metadata-types-ga)) — so they invented a records-that-are-metadata type to work around it. Vlocity then rebuilt Odoo's external-ID machinery in userland on top of that, with configurable "Matching Keys" defining row uniqueness. Trialforce, their tenant-snapshot mechanism, has no upgrade story at all: "Remember to generate a new template each time you make updates to your TSO." New templates affect future trials only.

**The baseline technique, and its documented hazard.** Django: "if you change one of the rows created by a fixture and then run `loaddata` again, **you'll wipe out any changes you've made**" ([initial data](https://docs.djangoproject.com/en/6.0/howto/initial-data/)) — Odoo's default branch with no escape hatch, which is why Django's own remedy is versioned data migrations instead. Rails seeds are the opposite default: "The code here should be idempotent," with the idiom `find_or_create_by!` — upsert by natural key with the update half omitted, which is closer to `noupdate="1"` plus `forcecreate`.

**Across Jira, GitLab, Asana and Monday there is zero documented mechanism for re-applying an updated template to an already-provisioned tenant.** Where propagation exists, it is because the configuration was referenced rather than copied — Jira's shared schemes, Asana's Bundles ("Every time you edit or update a bundle, these changes will be reflected in all projects using that specific bundle"), Monday's Managed templates. Nobody has built a merge engine over a copy. Jira's documented procedure for changing a project's template is to create a new project and bulk-move the work items.

Two design ideas worth stealing regardless of which strategy ROUTIQ picks. Atlassian makes copy-versus-reference a **per-entity** decision reduced to one token in their PCRI addressing scheme (`pcri:permissionScheme:id:10001` versus `pcri:notificationScheme:ref:notification1`), with an explicit `onConflict` policy of `FAIL`/`USE`/`NEW`. And ServiceNow inverts the marker: it tags the customer's edits, not the vendor's rows, so "The upgrade process skips changes to objects that have entries in the table" and cost scales with edits rather than shipped rows. **ROUTIQ gets that inversion nearly free** — a seeded row whose `created_by_command_id` points at a command later than the provisioning command has been edited by the tenant.

One caution from Odoo's own docs, which every system in this survey shares: "Data created by previous versions of the module (like removed fields) will not be automatically deleted… the simplest way to handle this is to start with a fresh database." Deletions and type changes are where seed replay degrades into an imperative migration script. **Plan the replay for insert and update only; route removals through explicit versioned commands.**

## 7. The escalation ladder

The rungs, with the evidence that justifies climbing to each. ROUTIQ sits on rung 1 for templates and rung 2 for categories and approvals.

**Rung 1 — hardcoded presets in code.** Where `TEMPLATES` in `templates.ts` lives now. Hadlow's midnight. Correct while the set of variants is small and known, and the deploy cycle is fast. Justification to leave: you are rebuilding and redeploying to change values that are not code — Hadlow's 2 o'clock trigger, "we find ourselves rebuilding and re-deploying it just to change a few numbers."

**Rung 2 — per-workspace config tables, edited only through commands.** Where `categories`, `approval_rules` and `workspace_modules` live. This is where every vertical product in §8 sits and where most of them stop. Justification to arrive: a tenant needs a value the other tenant does not, and the value drives display or grouping rather than computation. Evidence that it is enough: five of five surveyed products model job types, statuses, service tasks and trades this way.

**Rung 3 — required-field lists and field definitions as data.** ServiceTitan's job type carrying its own required-field set. Still not an engine: the field *types* stay a closed enum of three or four, and there is no designer. Justification to climb: a third tenant with a genuinely different required-field list, i.e. Brooks's third system, where you finally learn "those parts of [your] experience that are particular and not generalizable." **This trigger has not fired for ROUTIQ.**

**Rung 4 — a declarative rules interpreter or workflow graph.** Hadlow's 6 o'clock. The documented triggers, all first-party: engineers spending more time on workflow infrastructure than business logic, in-flight cases breaking on every deploy, process state scattered across logs and ad-hoc tables (Camunda); needing cross-team visual representation or multi-service orchestration (AWS); customer-authored unbounded states (the Jira line). **None of these is "the approval logic got complicated."** The failure mode on arriving early is documented by Camunda's own co-founder as four of his seven sins.

Two calibration points on tenant count. Microsoft puts the automation threshold at "**often around 10 or more**" tenants and the control-plane threshold at "fewer than 10 tenants" for manual operations. Salesforce built its metadata kernel for "tens of thousands of tenants." There is nothing in between in the published literature, which is itself informative: **at tens of tenants, nobody credible is recommending an engine.**

The support-load signal is the one to actually watch, and Microsoft states it: "You might notice that your team spends an increasing amount of time and effort on tenant management. Or you might notice bugs or operational problems because of inconsistencies in how team members perform management tasks."

## 8. How vertical fleet and field-service SaaS handle business-type variance

Read against the products' own API schemas where available — Fleetio's [OpenAPI schema](https://developer.fleetio.com/schemas/2025-05-05.yaml) and Odoo's source on GitHub carry the real answers, since the help docs are vague in exactly the places that matter. Jobber's developer and help sites and Samsara's knowledge base all returned 403 to automated retrieval; Jobber claims below rest on search-index extracts and are flagged.

**Fleetio contains both designs in one product, which makes it the clearest case.** `Issue.state` is `enum: [Open, Closed, Resolved]` — hardcoded, because resolution semantics depend on it. `VehicleStatus` is a CRUD row with `account_id, name, default, color, position` and nothing else, and the help centre confirms it drives nothing: the shipped values are editable and deletable, users can "Add your own custom Statuses," and "Vehicle Statuses do not affect Service Reminders" or "your Account Billing." `WorkOrderStatus` is the middle case — a user-owned row carrying exactly one load-bearing bit, `completed`, documented as "Whether Work Orders will be set to `completed` when they are moved to this status." Purchase orders show the dual-track design explicitly: the record carries both a fixed `PurchaseOrderState` enum and a separate `purchase_order_status_id`, with transitions as fixed named endpoints. Fleetio's terminology support is one toggle: "Selecting 'Asset' will change the word 'Vehicle' to 'Asset' in both the Fleetio web app and Fleetio Go."

**Samsara made the form's content infinitely configurable and its lifecycle completely fixed** — twelve field types, but seven form statuses in a closed set with fixed transitions. Its custom-attribute type system is deliberately minimal ("Indicates if the attribute is a `string` or a `number` type"), and tellingly the docs' own example use case is "asset types for assets" — Samsara declined to model asset type at all and pushed it into a key/value bag. Their immutable-revision rule is worth copying verbatim: "As form templates evolve and fields are added or removed… **new immutable revisions are created to keep any related form submissions and revisions of templates stay in lock step**," with every submission pinning `revisionId`.

**ServiceTitan answers the multi-trade question directly, and it is the most relevant answer for trucking versus passenger transport.** No separate products, no code branching: one schema with Business Unit as the pivot, tagged on two user-defined axes — "**Trades:** Specialties, such as HVAC, Electrical, or Plumbing" and "**Divisions:** Departments, such as Install, Sales, Service, or Maintenance," and "You can create your own custom trades and divisions" ([best practices for business units](https://help.servicetitan.com/docs/best-practices-for-managing-business-units)). The BU row carries all the real variance: customer-facing official name, licence number, currency, invoice header and footer, tax rate, warranty amount, overtime rules, payroll fees, accounting class, print templates. **"HVAC versus plumbing" is a row with different financial coordinates; posting behaviour stays in code.** Job statuses, by contrast, are fixed and *derived* rather than set — "As soon as the first technician is dispatched, the job moves to In Progress" — the opposite call to Fleetio, and for the right reason: ServiceTitan computes status from dispatch events, so the states must mean something to code.

**Odoo shows both calls inside a single module.** `fleet.vehicle.state` is a table with three fields; `FUEL_TYPES`, `vehicle_type`, `transmission` and the unit enums are Python constants. Note the direction — **fuel type is code and vehicle status is data, the exact opposite of Fleetio** — because the two products compute different things from them. `crm.stage`'s docstring records the migration away from enums: "Main CRM objects… will now use only stages, instead of state and stages," with `is_won` as the marker flag. And `account.move.state` is `Selection([('draft',…),('posted',…),('cancel',…)])`, `required=True, readonly=True`. **Stages are rows; posting states are enums.** That maps one-to-one onto ROUTIQ's own line between activity categories and financial entry status.

Odoo also demonstrates the trap ROUTIQ should avoid while making categories editable. Its defaults ship as XML data, but `fleet_vehicle.py` reaches back to specific seeded rows by external id — `self.env.ref('fleet.fleet_vehicle_state_waiting_list', raise_if_not_found=False)`. That `raise_if_not_found=False` is Odoo defending against a customer having deleted a row its own code depends on. Fleetio's marker boolean avoids the problem entirely and is strictly the better design.

**Cross-product answers to the lead's questions:**

- *Arbitrary workflow graph or approval chain?* **Zero of five.** Ceilings: Fleetio is trigger plus four actions, with approval as role plus dollar threshold. Samsara has one hardcoded approval hop. ServiceTitan has condition to business-unit assignment. Odoo has multi-step ordered per-button approvals with an "Approval Order" number — the richest here, and still a linear list. If Odoo, which offers a code-execution escape hatch, still models approval as an ordered list of role-scoped steps, a graph is not needed.
- *Per-customer terminology renaming?* **Almost universally no.** Fleetio and Jobber each offer a single named alias for a single noun. ServiceTitan and Samsara offer nothing. Odoo gets it only as a side effect of stage names being customer-owned translatable rows. Worth noting ServiceTitan's business unit carries both an internal name and a separate customer-facing "official name" — **the split that matters in this category is internal versus client-facing, not per-tenant vocabulary.**
- *Multiple business types?* **One schema, classified by rows, in every case.** Nobody ships separate products. Fleetio's "vehicle" spans boats, forklifts and excavators.

## What NOT to build yet

Each item names the trigger that would change the answer, so this section is a checklist rather than a prohibition.

**Do not build a field designer, a metric definition engine, or any FieldDefinition/WorkflowPolicy/ReportDefinition table.** §13 decision 1 already refused this and the research supports the refusal without qualification. Salesforce's kernel exists to amortise across tens of thousands of tenants and costs a shadow query optimizer, a shadow statistics system, five write-amplifying pivot tables and a governor regime to sustain. *Trigger to revisit:* nothing short of hundreds of tenants with genuinely divergent schemas, and even then ServiceNow proves you can be dictionary-driven without a universal data table.

**Do not adopt BPMN, Camunda, Temporal, or any workflow engine.** The operational footprint alone contradicts §6a's requirement that `docker-compose.yml` run the full stack cold. Camunda's own replacement trigger has not fired; Ruecker's sins list shows four of seven failure modes come from adopting an engine. *Trigger to revisit:* in-flight approvals breaking on deploy, or process state genuinely scattered outside the `approval_rules`/status model.

**Do not build a workflow graph or a state-machine designer for approvals.** Zero of five surveyed products offer one, and Salesforce, SAP, Ramp and Odoo all converged on an ordered list of role-scoped steps. *Trigger to revisit:* a pilot operator needing sequential multi-role approval — and even then the change is a `step_order` column on `approval_rules` plus ordered evaluation, not a graph.

**Do not build the general per-tenant terminology override layer.** Two of five products in the category ship a single-noun toggle; the rest ship nothing. Category labels already cover the nouns that actually vary between trucking and passenger transport. *Trigger to revisit:* a tenant asking to rename a *fixed* noun (Activity, Asset, Leg) rather than a category. When it comes, the mechanism is i18next `fallbackNS` with a tenant namespace over the base catalogue, scoped to a short closed list of renameable keys — and it must carry gender for French agreement, per Fluent's terms model.

**Do not make lifecycle or completeness states configurable.** These are computed with, so per the survey's central rule they stay enums. `COMPLETE_WITH_EXCEPTIONS` and the SOLD/RETIRED/WRITTEN_OFF transitions drive invariants. *Trigger to revisit:* none foreseeable — if a tenant wants different vocabulary for a state, that is a label, and the dual-track pattern (fixed enum plus a customer-named label on the same record, as on Fleetio's purchase orders) is the answer.

**Do not add per-tenant code branches, per-tenant deployments, or a per-client fork.** Both AWS and Microsoft name this as the antipattern; §13 decision 24 already refused it. *Trigger to revisit:* none. This one is not a rung on the ladder.

**Do not build a merge engine for re-applying updated seed bundles.** Nobody in the survey has one. Jira, GitLab, Asana and Monday document no re-apply mechanism at all; Odoo and ServiceNow use per-record policy flags plus a review queue; Django and Salesforce overwrite unconditionally. *Trigger to revisit:* none at pilot scale. Plan seed replay for insert and update only, and route removals through explicit versioned commands.

**Do not turn `custom_values` into an EAV table.** The JSONB column validated per template in the command layer is the cheap correct version. *Trigger to revisit:* needing to index or aggregate across custom fields — at which point the answer is a real column, not a pivot table.

**Do not expand the custom-field type system beyond four types.** Fleetio ships four, ServiceTitan three, Samsara two for attributes. Fifteen means you have become a platform.

**Finally, do not let the seed bundles stay in test code.** This is the one item in this document that is a defect rather than a deferral. Everything above assumes a production provisioning path exists; today it does not.
