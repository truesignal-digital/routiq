Core and modules

The direction for everything new: the application is its core; every feature beyond it is a module that can be plugged in or out per company without breaking anything. This page fixes what counts as core, the contract every module follows, and how a user reaches each module's pages.

Is it core or a module?

  • Core if every company needs it to use ROUTIQ at all, or other parts depend on it (who you are, where you work, who approves, what happened).
  • Module if a company could reasonably live without it, or it only fits one kind of operator.
  • When unsure, it's a module. Moving a module into core later is easy; pulling something out of core is not.

What "plug in / plug out" guarantees

  • Turning a module on: its sidebar rows, tabs, buttons, Home cards and fields appear for the roles allowed.
  • Turning it off: all of that disappears; the data stays, untouched, and comes back if it's turned on again.
  • A module another one needs can't be turned off first (Customers while Parcels is on).
  • Every module's "off" state is tested, not just its "on" state.

Today the module registry is a list of codes in packages/contracts/src/modules.ts and each screen checks its own flag; the manifest replaces those scattered checks.

Partners: what it looks like and what you do with it

Partners is a module, not a tab. It has one home under Company → Partners (connections are a company-level agreement, set by an Administrator), and it shows up in the two places where trips are handed over: sending a booking out from Planning, and receiving requests into the To-assign queue.
