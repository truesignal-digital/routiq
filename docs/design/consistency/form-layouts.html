Form layouts

A form's layout comes from what kind of form it is, not from whoever builds it. There are six layouts. Pick one with the questions below and the size, grouping, footer and phone behaviour are already decided. Building a form then means writing its fields in order and naming a layout.

Why

Why fixed layouts

Users

The same kind of form always looks the same, so the second form a driver opens already feels familiar. Amount sits in the same spot, with the submit button in the same corner.

Builders

No layout decisions per form. A new form is a field list + a layout name. The layout owns width, spacing, groups, footer, phone sheet and error summary.

Reviewers and tests

A test can check that each form declares a layout and that its field order matches its layout's rule. Screens drift less because there's less to choose.

Choose

Pick a layout in three questions

Is it a yes/no decision on a record that already exists (approve, reject, reverse, cancel, release, deactivate, close)?Decision
Does it have rows that repeat (cost lines, legs, crew, entries)?Line items
Is it a long capture, done over minutes, often offline, with more than ~14 fields?Long capture

Layout 1

Quick entry

For the things people log many times a day. Six fields or fewer, no group headings when there are three or fewer, the amount or the main value first and large. Opens with today's date and the context filled in, so most entries need two or three taps.

Rules

  • Main value first, large on phone (52 px).
  • Date/time as quick chips (Now, Earlier today, Pick…) instead of a picker first.
  • No optional fold if every field is required; otherwise one fold.
  • Used by: Log fuel, Add note, Record a reading, Attach a receipt, Record expense / revenue.
Layout 2

Record

The default. Seven to fourteen fields in two to four groups, required first, optional folded. Used for anything that creates or edits one record: a problem, a work order, a document, a person, a user, a branch.

Rules

  • Groups named in plain words ("What", "Who and how much", "Proof").
  • Each group 1 to 4 fields. More than 4 groups means it's a Long capture.
  • Pickers for people and vehicles are search fields; if the page knows the value, it is pinned instead.
  • Money always with its unit as a suffix (XAF), never in the label.
  • Used by: Report a problem, Open / complete-without-costs a work order, Add or renew a document, Register a person, Add a user, Add a branch, Substitute a vehicle, Record a trip leg.
Layout 3

Line items

For forms where part of the record repeats: the cost lines when a work order is completed, legs and crew on a trip, entries on a trip sheet. Header fields on top, then a row table with one "Add a line" button, then a running total. The panel widens to 560 px; on phone each row becomes a card.

Rules

  • Starts with one empty row (or none when "No cost" is the common case), never with zero rows and a lonely button.
  • Row columns: description, one category, the amount right-aligned. More than four columns means a row editor in its own panel page.
  • Running total under the rows, always visible. Postings sum exactly to the entry.
  • Remove is a 44 px icon at the row end; removing a filled row asks nothing but shows "Undo" for 5 s.
  • Errors sit on the row's field; the summary says "Line 2: amount".
  • Used by: Complete a work order (cost lines), trip sheet legs, crew and entries.
Layout 4

Decision

A dialog with three parts: what you're deciding about (a short summary of the record), what happens after, and at most one field (the reason). Buttons repeat the verb.

Rules

  • Title is a question naming the record.
  • Summary: 2 to 4 facts that let the person check it's the right record.
  • Negative decisions: reason required, marked, max 500, destructive button.
  • Positive decisions with no field (approve, close period): no dialog when undo is cheap; otherwise this layout without the field.
  • Used by: Reject / approve with note, Reverse, Cancel, Dismiss, Release to service, Reopen, Deactivate, Close period, Discard draft.
Layout 5

Long capture

Its own page. A 760 px column under the breadcrumb, each group a card with a status ("Done", "1 missing"), two columns inside cards on desktop, a sticky footer with progress and "Save draft". On phone, each card is a step, and the last step is a review with a "Change" link per answer. See the drawing on the form system page.

Rules

  • Sections in task order (vehicle and driver → route → departure → load → money).
  • Inside a section, the pair list applies, plus any two short fields of the same section (two columns ≥ 768 px).
  • Repeating parts inside use the Line items rules.
  • Draft saved locally on every change; "Draft saved 07:42" in the top bar.
  • Leaving with changes keeps the draft; there's no discard dialog unless the person asks to discard.

Used by

  • Record a trip (journey / haulage sheet)
  • Register a truck
  • Nothing else today. A form only becomes a page if it fails the Record limits (more than 4 groups or 14 fields).
Layout 6

Edit in place

Only for a record's Details tab (#84). The facts card turns into fields in the same groups and order; the 3-column display grid folds to 2 columns of fields; the footer appears inside the card. Everything else edits in a panel with the form that created the record.

Build

In code: a form is fields + a layout name

The layout lives in one component. A form file declares its layout and its groups; it contains no spacing, widths or footer markup. The same definition renders as a panel on desktop, a sheet on phone, or steps for a Long capture.

// apps/web/src/vehicle/forms/LogFuelForm.tsx  (proposed shape)
export function LogFuelForm(props: LogFuelProps) {
  const form = useCommandForm(logFuelSchema, "record-expense", 1, {
    defaults: { at: now(), assetId: props.assetId },
  });
  return (
    <FormLayout
      kind="quick-entry"
      form={form}
      title={t("vehicle.logFuel.title")}
      hint={t("vehicle.logFuel.hint")}
      submit={t("vehicle.logFuel.submit")}
      pinned={<PinnedVehicle asset={props.asset} />}
    >
      <FormGroup title={t("form.group.howMuch")}>
        <FormPair>
          <MoneyField name="amount" />
          <QuantityField name="litres" unit="L" />
        </FormPair>
        <DateTimeField name="at" quick={["now", "earlierToday"]} />
      </FormGroup>
      <FormGroup title={t("form.group.odometer")}>
        <ReadingField name="odometer" last={props.lastReading} />
      </FormGroup>
      <FormOptional>
        <TextField name="station" />
        <FileField name="receipt" camera />
      </FormOptional>
    </FormLayout>
  );
}

What the pieces own

  • FormLayout kind: surface, width, header, pinned block, error summary, footer, phone sheet or steps, focus on open, discard prompt.
  • FormGroup: heading and the 24 px rhythm; hidden heading when the form has ≤ 3 fields.
  • FormPair: two columns; a lint checks the pair is on the allowed list (by field kinds).
  • FormOptional: the fold with its filled count; auto-opens on error.
  • Field kit: label, required marker from the schema, help, error, 44 px.
  • useCommandForm: react-hook-form + contract schema + command intent + idempotency key per open + status.

Tests that come free

  • Each *Form.tsx renders a FormLayout with a known kind.
  • Quick entry has ≤ 6 fields; Record ≤ 14 fields and ≤ 4 groups (counted from the schema).
  • The six harness tests from the recipe.
