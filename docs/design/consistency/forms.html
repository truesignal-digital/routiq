Form system

One rule decides where a form opens, one field kit decides how each field looks, and one recipe decides how a form gets built and tested. Every form a user fills in ROUTIQ should come out of these three.

Decision

Three surfaces, chosen by the job

The question is not "how big is the form" but "what is the user doing". Recording or changing a fact opens a panel. Making a decision opens a dialog. Capturing a long multi-part record opens a page.

Frame

  • Title is the action as a verb phrase, the same words as the button that opened it.
  • The submit button repeats that verb ("Record expense"), never "Save" or "OK".
  • Submit is always the last button: right on desktop, right half on phone. Cancel sits before it. Today CommandForm puts submit first in panels and last in dialogs.
  • The footer hint says what happens after submit (approval, who sees it).

Content

  • What the page already knows (vehicle, branch, work order) is pinned, not asked.
  • Group order: what, how much, when, proof, more details.
  • Required fields first, marked with a red asterisk. Optional fields fold into "More details (optional)" with a filled count.
  • Defaults: today's date, the context branch, the last reading as a hint.

Behaviour

  • Closing with typed data asks "Discard this expense?" (dialog rules).
  • Escape and the × close; the browser Back closes the panel, not the page.
  • Phone: the sheet fills the screen, the footer stays above the keyboard.
  • After submit: the panel closes, a toast confirms with "View", and the record shows as pending (ADR-0001).

Shared rules

  • Label above the field, sentence case, no colon.
  • Every control is at least 44 px tall (48 px for the main amount on phone).
  • Labels, help and errors all come from t(); error text maps from the contract's codes.
  • Two fields share a row only when they belong together (amount + date, date + time).
  • The field reads back in the record panel with the same label, in the same group.

ADR-0008

Edit and correct look the same to the user

"Edit" opens the same form the record was created with, prefilled, in the same surface. What happens underneath depends on the record (ADR-0008): a plain edit, an author editing their own pending entry, or a correction that reverses and re-records. When it is a correction, the form says so with a banner, shows old → new on each changed field, and asks for a reason.

Reproduce

Recipe: build a new form in five files

A form should take an afternoon, not a week. The recipe fixes the files, the order and the tests, so every form arrives with the same checks.

Files

  1. packages/contracts/src/commands/<name>.ts: payload schema + field helpers (already the command rule).
  2. apps/web/src/<feature>/<Name>Form.tsx: useCommandForm(schema, command) + <CommandForm surface> + field-kit fields. No layout code beyond groups.
  3. <Name>Form.test.tsx: the six standard tests below, from test/form-harness.ts.
  4. i18n/locales/{fr,en}.json: <feature>.<name>.{title,description,submit,submitting,hint,success} + field labels.
  5. .agents/skills/verify-routiq/features/<feature>.md: one "open, fill, submit, see it" recipe line.

Six standard tests (one harness, one line each)

  1. Opens with the pinned context and defaults filled.
  2. Submit with empty required fields shows the summary and sends nothing.
  3. A valid fill sends exactly the expected payload through commandClient.
  4. A server error code shows its translated banner and keeps the values.
  5. VERSION_CONFLICT replaces the form with Refresh.
  6. Success closes the surface and calls notifyCommandSuccess.

Guards (tests that fail the build)

  • No type="date" / datetime-local anywhere in src/.
  • Dialog containing a <form> only in the allow-list of decision dialogs.
  • Every *Form.tsx has a sibling test that calls the harness.
  • Submit labels are not "Save"/"OK"/"Valider" alone (key lint on *.submit).
  • No useState-driven forms: every form goes through useCommandForm.

Done means

  • Typecheck and the form's test file pass.
  • pnpm verify drive shows it open on desktop and phone, filled, submitted, and the stored row read back through the API.
  • Screenshots in fr and en; walkthrough video in English on the PR.
