Super admin, tenants, and keeping it small

Three questions: is this direction overwhelming the application; can ROUTIQ have its own super admin that runs the setup tool; and how do companies stay isolated while still being able to work with each other.

Honest answer

Is this already too much?

The risk is real

  • Customers, parcels, stock, purchasing, scheduling, timetables, a vendor console: built together, that's three products' worth of work for a two-tenant pilot.
  • Every module adds screens to test, words to translate (fr and en, two presets), roles to check, and support questions.
  • The danger isn't the platform being big. It's half-built modules: screens that exist but that nobody uses well, which erode trust (the owners' "trust ladder").

Why it can still stay sustainable

  • Each person sees a small app. A driver sees 3 places; a cashier 3; a technician 4. The platform grows, not each person's screen (see below).
  • Modules are off unless sold. A trucking tenant without stock never sees stock; the code is there, the UI isn't.
  • One system for every screen. Same five page types, same six form layouts, same role table. A new module reuses them; it doesn't invent screens.
  • The core stays small and never depends on a module. Modules plug into it (commands, reads, sidebar rows), so removing one never breaks another.
Recommendation: build in this order, one at a time, and only when a tenant will use it
1 · Roles change + consistency fixes (foundation) → 2 · Scheduling (trucking value, builds on trips) → 3 · Customers (both presets) → 4 · Super admin console (needed once there are more than ~3 tenants) → 5 · Parcels (when a bus tenant signs) → 6 · Stock (when a workshop asks). Each one ships with its walkthrough video and its "off" state tested before the next starts.

Super admin

Our own super admin console on a console. subdomain: yes, and most of it exists underneath

What already exists

  • A vendor operator identity, separate from every tenant's users (VENDOR_OPERATOR principal).
  • Platform-scope commands: provision-workspace (company + branches + first admin + modules + presets in one audited step) and enable / disable module (ADR-0005).
  • A CLI script that runs provisioning today (apps/api/scripts/provision.ts).

What the console adds

  • A separate web app for ROUTIQ staff only (its own address, its own login with a second factor), never a hidden page inside the tenant app.
  • It calls the same command API with platform scope, so every action is audited like any other command.
  • Same design system (neutral theme), with a dark sidebar and a red "Platform" badge so staff always know they're not inside a customer's app.

What the console shows about a tenant

  • Setup facts: preset, modules, agencies, administrators.
  • Health: active users, records per week, errors, storage, last activity.
  • Not their business data (trips, money, customers). Those need support access (below).

Actions

  • Toggle a module: a small confirm with a reason, then it appears or disappears for that company; data is kept; a module another one needs is locked ("required by Parcels").
  • Add an agency, add or reset the first administrator.
  • More: suspend the tenant (read-only), export their data.

Trust

Support access: only when the company says yes

In the tenant app (administrator)

ROUTIQ support asks to view your workspace
Reason: "Parcels not showing on the 14:00 journey". Read-only, until today 18:00.
While allowed: a banner shows "ROUTIQ support can view until 18:00 · Stop now" on every page for administrators, and every page support opens is written in your History.

Rules

  • Default: ROUTIQ staff see no business data.
  • Support asks with a reason; the tenant administrator allows it for a set time, read-only. They can stop it at any moment.
  • Everything viewed is logged in the tenant's own history and in the platform audit.
  • Writing on a tenant's behalf is never possible from the console; changes go through the tenant's own people.
Under the hood

Tenant isolation

"Underneath it works like a tenant" is already how ROUTIQ is built: every business record carries its company (workspace_id), references between records include it so a record can't point at another company's record, and the server decides the company from the login, never from the screen.

Later

Companies working together

Isolated by default doesn't have to mean they can never work together. A trucking company may pass a job to a partner company that also uses ROUTIQ, or a shipper may want to follow its trips. That should happen through an explicit connection, never by sharing records.

How it would work

  • Both companies agree to connect (invite + accept); either can disconnect.
  • A trip request is a message with chosen fields (date, route, cargo, price). Accepting creates a copy in the receiving company; each keeps its own record and history.
  • Afterwards only status flows back (planned, started, closed, and when it was delivered), never money, drivers or other data.
  • Every exchange is logged on both sides.

Recommendation

Not for the pilot. It needs its own architecture decision and two companies that actually want it. Isolation stays the default and the guarantee; connections are an add-on, and the "Partners" page only exists once that module is on.
