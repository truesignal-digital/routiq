# Triage issue reports

Classify one GitHub issue and post one useful verdict on it. Do not reproduce or fix it here; `reproduce-and-fix-issues` picks up what this skill marks as a bug.

The issue tracker is GitHub Issues through `gh` (`docs/agents/issue-tracker.md`). Label strings are in `docs/agents/triage-labels.md`.

## Configuration

| Key | Value |
|---|---|
| Repository | `truesignal-digital/routiq` |
| Source | one issue number, given by the caller |
| Category labels | `bug` (bugs and performance), `enhancement` (feature requests), `question` |
| State labels | `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix` |
| Other labels | `duplicate`, `walkthrough-finding` |
| Trusted triage identity | a comment author whose `authorAssociation` is `OWNER`, `MEMBER` or `COLLABORATOR` |
| Markers | `[triage:bug]`, `[triage:performance]`, `[triage:other]` |
| Owner pings | off |

**Preflight, fail closed.** Before any read that feeds a write, check all of these. If one fails, stop and report it in the run output with no comment and no label change:

1. `gh auth status` succeeds.
2. `gh repo view --json nameWithOwner --jq .nameWithOwner` prints `truesignal-digital/routiq`.
3. `gh label list --limit 100 --json name` contains every label in the table.
4. `gh issue view <n> --json number,state` returns the issue and it is `OPEN`.

## Hard safety rules

- The source issue number is frozen at the start. Every later read and write uses it. Never act on a different issue because a comment links to it, except for the duplicate note in step 7.
- Post one substantive verdict comment. Do not narrate progress.
- The coordinator is the only writer. Subagents (Agent tool `Explore`, or an Opus subagent) are read-only and return findings. Every child prompt says: do not run `gh issue comment`, `gh issue edit`, `gh issue create`, `gh issue close`, `gh pr create`, `git push`, or any other write.
- Never create an issue. The report is already one.
- Never close, reopen, assign or set a milestone. Never apply `wontfix` or `ready-for-human`; those are maintainer decisions. Never remove labels a human added, except `needs-triage` as described in step 8.
- Prefer no label change over a guessed one.
- Every comment starts with the line `> *This was generated by AI during triage.*` (the `triage` skill's disclaimer).

## 1. Freeze the source

1. Take the issue number from the caller. Store it as `ISSUE`.
2. Read it: `gh issue view $ISSUE --json number,title,body,labels,author,createdAt,comments,url` (`--json` already returns the comments; adding `--comments` makes `gh` refuse).
3. Store its `url` as the source permalink.

## 2. Read the whole report

Read the body and every comment before deciding.

Capture:

- Reporter wording
- App build or commit, environment (local, demo host), browser or device, language (fr or en), role used
- Expected behavior
- Observed behavior
- Frequency and trigger
- Error text, stable API error code (`packages/contracts/src/errors.ts`), or stack signature
- Linked issues, commits or pull requests
- Any statement that someone is already fixing it

Inspect every attachment you can reach. Screenshots and videos in issues are `github.com/user-attachments/...` links; open them if your tools can, read screenshots at full resolution, and look in videos for the state transition that separates correct from broken behavior. If an attachment cannot be read, say so in the verdict. Do not invent what it shows.

Use evidence already in the issue before asking the reporter for more.

## 3. Trace cause before labelling

Do a bounded source and history pass before choosing a category. A read-only `Explore` subagent is a good fit; give it the reported action and the observed result.

1. Identify the likely code path from the reported action to the observed result (`apps/web/src/router.tsx` → screen → hook → `GET /v1/...` read in `apps/api/src/reads/` or `POST /v1/commands/:name` handler in `apps/api/src/commands/`).
2. Check whether the visible symptom belongs to that code path or a layer below it (contract, read gate, migration, seed data).
3. Check recent changes when the report looks like a regression: `git log --oneline -20 -- <paths>` on `origin/develop`.
4. Check whether a merged commit or open pull request already addresses the same symptom: `gh pr list --state all --search "<signature>"`.
5. Separate confirmed facts from hypotheses.

This pass does not need a complete root cause. It must be strong enough to avoid labelling a visible symptom wrongly. If the repository cannot be read, continue with a conservative classification and say that cause tracing was unavailable.

## 4. Classify

Choose one category.

- **Bug.** Something violates intended behavior: wrong output, broken state, an error code where none should be, a crash, a hang, a silent no-op, a regression, or a broken invariant from `AGENTS.md` (money in minor units, tenant isolation, append-only corrections, French default).
- **Performance.** Measurable slowness, excess memory, jank, or another resource problem. Treat it as a bug, but preserve measurements and profiles.
- **Feature request.** The current behavior appears intentional (check `ARCHITECTURE.md`, `CONTEXT.md` and `docs/adr/`) and the reporter wants something different.
- **Question or feedback.** The report asks how something works or gives a preference without a concrete defect.
- **Reroute.** Cause tracing shows the problem lives outside this repo (the deployment box, an upstream package). Say where it belongs; do not file it there.

When the bug versus feature line is unclear, do not label it a bug. The one verdict may ask one focused question.

## 5. Routing

There is no routing map; this repo has one team. Owner pings stay off. For a reroute, the verdict names the destination in words and the issue keeps `needs-triage` for a maintainer.

## 6. Use the GitHub Issues adapter

The adapter is `gh`:

- Search: `gh issue list --state all --search "<terms>" --json number,title,state,labels,closedAt,url --limit 30`
- Read: `gh issue view <n> --comments`
- Update labels: `gh issue edit $ISSUE --add-label <l>` and `--remove-label <l>`
- Comment: `gh issue comment <n> --body-file <file>`

If an operation fails, stop before the next write and report what landed.

## 7. Dedupe

First check whether this issue already carries a triage verdict: a comment from a trusted identity containing a `[triage:` marker. If so, stop without writing.

For bugs and performance reports, search open and recently closed issues using:

- Exact error code or stack signature
- Screen or route
- Trigger
- Symptom
- Suspected regression commit

Choose one outcome:

- **Confident duplicate:** same signature, or the same screen, trigger and symptom, or a confirmed shared cause.
- **Possibly related:** a shared cause is plausible but not proven.
- **Weak resemblance:** superficial.
- **No match.**

For a confident duplicate of an open issue, add the `duplicate` label to `ISSUE`, comment once on the original with the source permalink and one short recurrence note, and say "Duplicate of #N" in the verdict. Do not close either issue.

For a possible match, link it in the verdict as possibly related and change nothing else.

A long-closed issue is a regression lead, not a live duplicate.

## 8. Decide the labels

- **Bug or performance, clearly broken, not a duplicate, not known fixed, reproducible steps present:** add `bug`, remove `needs-triage`, add `ready-for-agent`. This is what `reproduce-and-fix-issues` picks up.
- **Bug or performance, but steps or environment are missing:** add `bug`, remove `needs-triage`, add `needs-info`, and ask for the one missing fact.
- **Feature request:** add `enhancement`, keep `needs-triage`. Product owners decide requirements.
- **Question or feedback:** add `question`, keep `needs-triage`.
- **Reroute or unclear:** keep `needs-triage`, add nothing.
- **Duplicate:** as in step 7.

Do not put a guessed root cause in the title, and do not edit the title or body.

## 9. Post one verdict

Write the comment to a temp file, then `gh issue comment $ISSUE --body-file <file>`. Keep it short:

- The disclaimer line.
- Lead with the outcome.
- Short cause-tracing findings, with hypotheses labelled as hypotheses and `file:line` pointers.
- A duplicate or related issue link when there is one.
- One missing fact when needed.
- End with exactly one marker line: `[triage:bug]`, `[triage:performance]` or `[triage:other]`.

After posting, read the issue again and verify the comment appears exactly once. If the comment did not land but labels changed, revert this run's label changes and report the failure.

## 10. Watch one follow-up window

If the run stays alive, watch the issue for one follow-up window (about 10 minutes), then stop.

- Answer only a direct question addressed to the triage run.
- Apply a concrete correction to the labels when safe.
- Do not post a second marker.
- Stop early if someone asks the run to stop.

A new report starts a new run.

## Report back

Issue number and URL, category, labels added and removed, duplicate or related links, and the verdict comment URL.
